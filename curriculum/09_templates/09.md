# 1. Bevezetés a generikus programozásba

Ahhoz, hogy megértsük a C++ sablonok (templates) valódi erejét, először is meg kell ismernünk a paradigmát, amire épülnek: a **generikus programozást**. 

A programozás egyik legfontosabb alapszabálya a **DRY elv** (Don't Repeat Yourself – Ne ismételd önmagad!). Ha ugyanazt a logikát kétszer, vagy többször leírod a kódodban, az hibalehetőséget hordoz magában, és rémálommá teszi a karbantartást. 

Képzeld el, hogy írnod kell egy nagyon egyszerű algoritmust: egy függvényt, ami két érték közül visszaadja a nagyobbat.
Először megírod egész számokra (`int`). Aztán rájössz, hogy tizedestörtekre (`double`) is kell. Később kiderül, hogy az RPG játékod `Karakter` objektumait is össze kéne hasonlítani a szintjük alapján. Hagyományos esetben újra és újra le kellene másolnod ugyanazt a pár soros logikát, csak a típusokat átírva. 

A generikus programozás pont ezt a problémát oldja meg: **lehetővé teszi, hogy magára az algoritmusra (a logikára) fókuszálj, függetlenül attól, hogy az milyen adatokon (típusokon) fog operálni.**

### A sablonok (Templates) szerepe a C++-ban

A C++-ban a generikus programozás eszközei a sablonok. Nagyon fontos megérteni egy alapvető koncepciót: **a sablon önmagában nem futtatható kód!**

A sablon egy "tervrajz" vagy "süteményszaggató". Amikor írsz egy sablont, tulajdonképpen azt mondod a fordítóprogramnak (compiler): *"Itt van egy általános recept. Ha a jövőben szükségem lesz rá `int`-ekkel, kérlek, generáld le nekem a konkrét kódot. Ha `double`-ökkel hívom meg, akkor generálj belőle egy `double` verziót is!"*

Ezt a folyamatot hívják a C++-ban **metaprogramozásnak** (amikor a kódod ír kódot helyetted). A fordító a háttérben pontosan annyi specifikus függvényt vagy osztályt fog legenerálni (példányosítani), ahány különböző típussal te azt a programod során meghívtad.

### Kapcsolat az előző anyaggal: A statikus polimorfizmus

Az előző tananyagban nagyon sokat beszéltünk a dinamikus, futási idejű polimorfizmusról (öröklődés, `virtual` kulcsszó, ősosztály-mutatók). Annál a megközelítésnél a program futás közben (késői kötés) döntötte el, melyik függvényt kell meghívni.

A sablonok ezzel szemben a **statikus (fordítási idejű) polimorfizmus** legfőbb fegyverei:

1.  **Korai kötés (Early Binding):** A fordítóprogram már a fordítás pillanatában pontosan tudja, hogy milyen típusokkal dolgozol.
2.  **Maximális teljesítmény:** Mivel minden döntés előre megszületik, és a fordító dedikált, típus-specifikus kódot generál a háttérben, a sablonok használatának **zéró futásidejű költsége (overhead)** van.
3.  **Típusbiztonság:** Ha egy sablont olyan típussal próbálsz meghívni, ami nem támogatja a sablonban lévő műveleteket (például nincs rá megírva a `>` operátor), a program már fordítási időben, biztonságosan elszáll egy hibaüzenettel.

Van azonban egy ára ennek a sebességnek: mivel a fordító minden használt típushoz legenerálja a kód másolatát, a programunk lefordított mérete (a bináris fájl) nagyobbra nőhet. Ezt hívják *code bloat*-nak (kódhízásnak).

# 2. Függvénysablonok (Function Templates)

A generikus programozás legegyszerűbb és leggyakoribb formája a függvénysablon. Képzeld el azt a klasszikus problémát, hogy írnod kell egy függvényt, ami visszaadja két érték közül a nagyobbat.

Ha nem ismernénk a sablonokat, valami ilyesmit kellene csinálnunk (ezt hívtuk az előző anyagban függvény-túlterhelésnek, azaz *overloading*-nak):

```cpp
int findMax(int a, int b) {
    return (a > b) ? a : b;
}

double findMax(double a, double b) {
    return (a > b) ? a : b;
}
```

Látható, hogy a logika `(a > b) ? a : b` hajszálpontosan ugyanaz. Csak a típusok térnek el. Ha bejön a képbe a `float`, a `char`, vagy egy saját `Player` osztály, a kódunk hamar kezelhetetlenné duzzad. Itt jönnek képbe a függvénysablonok!

### A `template <typename T>` és a `template <class T>` szintaxis

A sablonokat a `template` kulcsszóval vezetjük be, amit egy kacsacsőrök `< >` közé zárt paraméterlista követ. Ezen a listán határozzuk meg a sablon típusparamétereit (általában nagy `T` betűvel jelöljük a *Type* szóból, de bármilyen érvényes azonosító lehet).



Kétféleképpen is felírhatjuk:
1. `template <typename T>` (Ez a modernebb, kifejezőbb és ajánlott forma).
2. `template <class T>` (A régebbi forma. A `class` szó itt nem azt jelenti, hogy csak osztályokat fogad el, primitív típusokat – mint az `int` – is ugyanúgy megeszik. Technikai szempontból a kettő teljesen megegyezik ezen a szinten).

Nézzük meg, hogyan néz ki a fenti `findMax` függvényünk egyetlen, elegáns sablonként:

```cpp
#include <iostream>

// The template declaration
// 'T' is a placeholder for ANY type that supports the '>' operator
template <typename T>
T findMax(T a, T b) {
    return (a > b) ? a : b;
}

int main() {
    // Type Deduction in action!
    std::cout << "Max of ints: " << findMax(10, 25) << std::endl; 
    std::cout << "Max of doubles: " << findMax(3.14, 2.71) << std::endl;
    std::cout << "Max of chars: " << findMax('A', 'Z') << std::endl;

    return 0;
}
```

Amikor a fordítóprogram meglátja a `findMax(10, 25)` hívást, a háttérben (fordítási időben) fogja a sablonunkat, a `T` helyére behelyettesíti az `int` típust, és legenerál egy valós, futtatható `int findMax(int, int)` függvényt. Ezt hívjuk **példányosításnak (instantiation)**.

### Automatikus típusdedukció (Type Deduction)

Ahogy a fenti `main` függvényben is láthatod, a híváskor nekünk **nem kellett megmondanunk** a C++-nak, hogy milyen típust használunk. A fordító elég okos ahhoz, hogy a paraméterként átadott értékekből (pl. `10` és `25`) kitalálja (dedukálja), hogy a `T` most egy `int` lesz. Ezt a kényelmi funkciót hívják automatikus típusdedukciónak.

### Mi van, ha a fordító összezavarodik? (Explicit típusmegadás)

Előfordulhat, hogy olyan értékeket adunk át, amiből a fordító nem tud egyértelműen dönteni. Mi történik, ha ezt írjuk?

```cpp
findMax(10, 3.14); // HIBA!
```

Az egyik paraméter `int`, a másik `double`. Mivel a sablonunkban mindkét paraméter `T` (tehát azonos típusúnak kell lenniük), a fordító megáll, és hibát dob, mert nem tudja, melyiket válassza a `T` helyettesítésére.

Ilyenkor két megoldásunk van. Az egyik, hogy **explicit módon (kifejezetten) megmondjuk a fordítónak**, milyen típusra generálja le a függvényt a hívás pillanatában, kacsacsőrök használatával:

```cpp
// We explicitly tell the compiler to treat 'T' as a double.
// The integer '10' will be implicitly converted to '10.0'.
double result = findMax<double>(10, 3.14); 
```

Ezzel a szintaxissal (`függvénynév<Típus>(paraméterek)`) átvesszük az irányítást, és a sablon pontosan úgy fog viselkedni, ahogy mi azt elvárjuk.

Feladatok: 1-2

# 3. Osztálysablonok (Class Templates)

A függvénysablonok nagyszerűek algoritmusokhoz, de mi a helyzet az adatok tárolásával? A valós szoftverfejlesztésben gyakran van szükségünk olyan adatszerkezetekre (például egy láncolt listára, egy veremre vagy egy egyszerű tároló dobozra), amelyek logikája teljesen független attól, hogy mit teszünk beléjük. Egy `Stack` (verem) ugyanúgy működik, ha egész számokat, és akkor is, ha RPG karaktereket tárolunk benne: a legutoljára betett elemet vesszük ki először (LIFO).

Erre a problémára nyújtanak tökéletes megoldást az osztálysablonok. Ahogy a sablonfüggvény egy "recept" függvények gyártásához, úgy az osztálysablon egy "tervrajz" komplett osztályok generálásához.



### Osztálysablonok szintaktikája: Deklaráció és adattagok

A szintaxis nagyon hasonló a függvénysablonokéhoz: az osztály deklarációja elé oda kell biggyesztenünk a `template <typename T>` varázsigét. Innentől kezdve a `T` (vagy bármilyen más név, amit választasz) egy létező, érvényes típusként használható az osztályon belül adattagokhoz, metódusok visszatérési értékeihez vagy paramétereihez.

Nézzünk egy egyszerű, generikus `Box` (Doboz) osztályt, ami képes eltárolni egyetlen, bármilyen típusú értéket:

```cpp
#include <iostream>

// The class template declaration
template <typename T>
class Box {
private:
    T item; // The stored item of generic type T

public:
    // Constructor taking a value of type T
    Box(T initialItem);

    // Method returning a value of type T
    T getItem() const;

    // Method to update the item
    void setItem(T newItem);
};
```

### Metódusok implementációja az osztályon kívül

Ez az a pont, ahol a legtöbb C++ tanuló először megakad. Ha a metódusokat nem magán az osztályon belül (inline) írod meg, hanem kívül, akkor a fordítónak **minden egyes metódus előtt újra a tudtára kell adnod, hogy ez egy sablonhoz tartozik**.

Ráadásul a hatókör-operátort (`::`) is fel kell vértezned a sablonparaméterrel, hiszen a `Box` önmagában már nem egy konkrét osztály neve, hanem csak egy sabloné. A teljes, helyes név: `Box<T>`.

Így néz ki a fenti metódusok külső implementációja:

```cpp
// We MUST repeat the template declaration for each external method
template <typename T>
Box<T>::Box(T initialItem) : item(initialItem) {}

template <typename T>
T Box<T>::getItem() const {
    return item;
}

template <typename T>
void Box<T>::setItem(T newItem) {
    item = newItem;
}
```

### Példányosítás (Instantiation): Így jönnek létre a memóriában

Amikor használni akarod az osztálysablont a `main` függvényben, van egy nagyon fontos különbség a függvénysablonokhoz képest: **az osztálysablonoknál (a C++17 előtti szabványokban) nincs automatikus típusdedukció!** 

Neked kell explicit módon, kacsacsőrök között megadnod, hogy milyen típussal szeretnéd példányosítani (létrehozni) az osztályt. Ekkor a fordító a háttérben legenerálja a memóriában a kért, specifikus osztályt.

```cpp
int main() {
    // 1. Instantiating a Box for integers
    // The compiler generates a 'Box_int' class behind the scenes.
    Box<int> intBox(100);
    std::cout << "Integer Box contains: " << intBox.getItem() << std::endl;

    // 2. Instantiating a Box for doubles
    Box<double> doubleBox(3.14159);
    std::cout << "Double Box contains: " << doubleBox.getItem() << std::endl;

    // 3. Instantiating a Box for strings
    Box<std::string> stringBox("Hello Templates!");
    std::cout << "String Box contains: " << stringBox.getItem() << std::endl;

    return 0;
}
```

Minden alkalommal, amikor egy új típust adsz meg a kacsacsőrök között (`<int>`, `<double>`, `<std::string>`), a C++ fordító létrehoz egy teljesen különálló, független osztályt a lefordított kódban. Ennek köszönhetően a sablonok használata ugyanolyan gyors futásidőben, mintha három külön osztályt (`IntBox`, `DoubleBox`, `StringBox`) írtál volna meg kézzel.


### Sablonok és Polimorfizmus találkozása (Haladó példa)

Most nézzük meg, mi történik, ha egy generikus osztályt és a korábban tanult dinamikus polimorfizmust (öröklődés, virtuális függvények) egyszerre akarjuk használni!

Tegyük fel, hogy írunk egy generikus `Storage` (Raktár) osztályt, amibe 2 darab elemet tudunk eltenni. Azt szeretnénk, ha ez a raktár képes lenne polimorfikus objektumokat (pl. különböző fegyvereket) tárolni. 

**A kritikus szabály:** Ahhoz, hogy a késői kötés (dinamikus polimorfizmus) működjön, a generikus típusnak (`T`) **mutatónak (pointernek)** kell lennie! Ha konkrét értékeket adnánk át, a C++ megpróbálná példányosítani az absztrakt ősosztályt, ami fordítási hibát okozna, vagy levágná a leszármazott egyedi adatait (object slicing).

Nézzük meg, hogyan kell ezt helyesen létrehozni a `main` függvényben:

```cpp
#include <iostream>

// 1. A generic storage template
template <typename T>
class Storage {
private:
    T items[2];
    int count;

public:
    Storage() : count(0) {}

    void add(T newItem) {
        if (count < 2) {
            items[count++] = newItem;
        }
    }

    T get(int index) const {
        return items[index];
    }
};

// 2. An abstract base class for Polymorphism
class Weapon {
public:
    virtual ~Weapon() = default;
    virtual void attack() const = 0;
};

// 3. Derived classes
class Sword : public Weapon {
public:
    void attack() const override { std::cout << "Slash with Sword!" << std::endl; }
};

class Bow : public Weapon {
public:
    void attack() const override { std::cout << "Shoot with Bow!" << std::endl; }
};

int main() {
    std::cout << "--- Templates meets Polymorphism ---" << std::endl;

    // CRITICAL STEP: Instantiating the template with a POINTER type (Weapon*)
    // We explicitly tell the compiler: "Create a Storage that holds Weapon pointers"
    Storage<Weapon*> armory;

    // Dynamically creating objects and storing their pointers in the generic storage
    armory.add(new Sword());
    armory.add(new Bow());

    // Retrieving the generic item (which is a Weapon*), and making a polymorphic call!
    std::cout << "Attacking from storage:" << std::endl;
    armory.get(0)->attack(); // Outputs: Slash with Sword!
    armory.get(1)->attack(); // Outputs: Shoot with Bow!

    // Don't forget to clean up dynamically allocated memory!
    delete armory.get(0);
    delete armory.get(1);

    return 0;
}
```

### Kódpélda: Sablonos tároló + Sablonos polimorfizmus

Amikor egy osztálysablonból örökölünk egy másik osztálysablonba, van egy nagyon fontos, haladó C++ szabály, amibe a legtöbben belefutnak: **a leszármazott osztályban az ősosztály adattagjait csak a `this->` mutatóval lehet elérni!** (Mivel az ősosztály típusa még nem ismert teljesen, a fordítónak explicit módon meg kell mondani, hogy az adattag az aktuális objektumhoz tartozik).

Nézzük meg, hogyan néz ki ez a "duplán sablonos", polimorfikus kód a gyakorlatban!

```cpp
#include <iostream>

// 1. The generic Storage template (same as before)
template <typename ItemType>
class Storage {
private:
    ItemType items[2];
    int count;

public:
    Storage() : count(0) {}

    void add(ItemType newItem) {
        if (count < 2) {
            items[count++] = newItem;
        }
    }

    ItemType get(int index) const {
        return items[index];
    }
};

// 2. The Weapon BASE CLASS is now a template too!
template <typename DamageType>
class Weapon {
protected:
    DamageType damage; // The damage can be int, float, double, etc.

public:
    Weapon(DamageType d) : damage(d) {}
    virtual ~Weapon() = default;

    virtual void attack() const = 0;
};

// 3. Derived classes must also be templates and inherit from the specific Weapon<DamageType>
template <typename DamageType>
class Sword : public Weapon<DamageType> {
public:
    // Passing the damage up to the base class constructor
    Sword(DamageType d) : Weapon<DamageType>(d) {}

    void attack() const override {
        // CRITICAL C++ RULE: When accessing a member of a templated base class,
        // you MUST use 'this->' (or Weapon<DamageType>::damage)
        std::cout << "Slash with Sword! Damage: " << this->damage << std::endl;
    }
};

template <typename DamageType>
class Bow : public Weapon<DamageType> {
public:
    Bow(DamageType d) : Weapon<DamageType>(d) {}

    void attack() const override {
        std::cout << "Shoot with Bow! Damage: " << this->damage << std::endl;
    }
};

int main() {
    std::cout << "--- Nested Templates & Polymorphism ---" << std::endl;

    // --- SCENARIO A: Weapons with INTEGER damage ---
    std::cout << "\n[Integer Armory]" << std::endl;
    
    // We create a Storage that holds pointers to Weapon<int> objects
    Storage<Weapon<int>*> intArmory;

    intArmory.add(new Sword<int>(50));
    intArmory.add(new Bow<int>(25));

    intArmory.get(0)->attack(); // Slash with Sword! Damage: 50
    intArmory.get(1)->attack(); // Shoot with Bow! Damage: 25

    // --- SCENARIO B: Weapons with FLOAT damage ---
    std::cout << "\n[Float Armory]" << std::endl;
    
    // We create a Storage that holds pointers to Weapon<float> objects
    Storage<Weapon<float>*> floatArmory;

    floatArmory.add(new Sword<float>(55.5f));
    floatArmory.add(new Bow<float>(30.2f));

    floatArmory.get(0)->attack(); // Slash with Sword! Damage: 55.5
    floatArmory.get(1)->attack(); // Shoot with Bow! Damage: 30.2

    // Memory Cleanup
    delete intArmory.get(0);
    delete intArmory.get(1);
    delete floatArmory.get(0);
    delete floatArmory.get(1);

    return 0;
}
```

### Mit látunk itt?
1. **Beágyazott sablonpéldányosítás:** Amikor létrehoztuk az első raktárat, a típusmegadás így nézett ki: `Storage<Weapon<int>*>`. Ez elsőre ijesztő lehet, de logikus: *"Egy olyan `Storage`, amibe olyan mutatókat teszünk, amik egész számot sebző `Weapon` objektumokra mutatnak."*
2. **Különálló öröklődési fák:** A C++ fordító a háttérben **két teljesen külön** ősosztályt és öröklődési fát generált! A `Weapon<int>` és a `Weapon<float>` technikailag két teljesen független osztály a memóriában, ezért nem tehetsz be egy float-ot sebző kardot az integer-es raktárba. Ez a C++ típusbiztonságának a csúcsa.

Feladatok: 3-4-5

# 4. Több sablonparaméter és alapértelmezések

Eddig minden példánkban csak egyetlen "joker" típust (a jó öreg `T`-t) használtunk a sablonjainkban. De a valóságban egy komplexebb adatszerkezetnek vagy algoritmusnak gyakran több, egymástól teljesen független típusra is szüksége lehet. 

Szerencsére a C++ sablonrendszere nem korlátoz minket egyetlen paraméterre!

### Több sablonparaméter (Multiple Template Parameters)

A klasszikus példa erre a "Kulcs-Érték" (Key-Value) párok tárolása, amit a programozásban szótárnak (Dictionary) vagy asszociatív tömbnek (Map) is hívunk. 

Tegyük fel, hogy szeretnénk eltárolni egy játékos nevét (ami egy szöveg) és a pontszámát (ami egy szám), vagy mondjuk egy szerver IP címét (szöveg) és a válaszidőt másodpercben (tört szám). Ehhez két független típusra van szükségünk.

A szintaxis pofonegyszerű: a kacsacsőrök `< >` közé vesszővel elválasztva több `typename` (vagy `class`) definíciót is felsorolhatunk. A konvenció szerint, ha az első `T`, akkor a másodikat `U`-nak (majd `V`-nek) szokás nevezni. Azonban a tiszta, olvasható kód (Clean Code) érdekében sokkal jobb beszédes neveket adni nekik!

```cpp
#include <iostream>
#include <string>

// Template with TWO independent types: KeyType and ValueType
template <typename KeyType, typename ValueType>
class KeyValuePair {
private:
    KeyType key;
    ValueType value;

public:
    // Constructor
    KeyValuePair(KeyType k, ValueType v) : key(k), value(v) {}

    void printData() const {
        std::cout << "Key: " << key << " | Value: " << value << std::endl;
    }
};

int main() {
    std::cout << "--- Multiple Template Parameters ---" << std::endl;

    // 1. String key, Integer value
    KeyValuePair<std::string, int> playerScore("PlayerOne", 9500);
    playerScore.printData(); // Key: PlayerOne | Value: 9500

    // 2. String key, Double value
    KeyValuePair<std::string, double> serverPing("192.168.1.1", 12.5);
    serverPing.printData(); // Key: 192.168.1.1 | Value: 12.5

    // 3. Integer key, String value
    KeyValuePair<int, std::string> errorLog(404, "Not Found");
    errorLog.printData(); // Key: 404 | Value: Not Found

    return 0;
}
```

Látható, hogy a kombinációk száma végtelen, és a C++ fordító minden egyes egyedi `K, V` párosításhoz legenerálja a megfelelő, típusbiztos osztályt a háttérben.

### Alapértelmezett sablontípusok (Default Template Parameters)

Ahogy a hagyományos függvényeknél megadhatunk alapértelmezett értékeket a paramétereknek (pl. `void setSpeed(int speed = 100)`), pontosan ugyanezt megtehetjük a sablonok típusainál is!

Ha tudod, hogy a sablonodat az esetek 90%-ában egy bizonyos típussal fogják használni (például a pontszám szinte mindig `int`), akkor adhatsz neki egy alapértelmezést az `= Típus` szintaxissal. Ha a programozó a példányosításkor kihagyja ezt a paramétert, a fordító automatikusan a megadott alapértelmezést fogja behelyettesíteni.

Nézzük meg ezt egy `ScoreBoard` (Eredményjelző) osztályon:

```cpp
#include <iostream>
#include <string>

// 'ScoreType' has a DEFAULT type of 'int'.
// If the user doesn't provide a second type, it falls back to 'int'.
template <typename PlayerType, typename ScoreType = int>
class ScoreBoard {
private:
    PlayerType player;
    ScoreType score;

public:
    ScoreBoard(PlayerType p, ScoreType s) : player(p), score(s) {}

    void display() const {
        std::cout << "Player: " << player << " scored: " << score << std::endl;
    }
};

int main() {
    std::cout << "\n--- Default Template Parameters ---" << std::endl;

    // We only provide the first type (std::string). 
    // The second type automatically becomes 'int'.
    ScoreBoard<std::string> standardMatch("Gandalf", 300);
    standardMatch.display(); // Player: Gandalf scored: 300

    // We explicitly override the default and provide BOTH types.
    // Now the score is a 'double'.
    ScoreBoard<std::string, double> precisionMatch("Legolas", 99.8);
    precisionMatch.display(); // Player: Legolas scored: 99.8

    return 0;
}
```

Az alapértelmezések használata sokkal tisztábbá és rövidebbé teszi a kódodat azokon a helyeken, ahol a sablont példányosítod, miközben megmarad a rugalmasság is, ha valami egyedi típusra lenne szükség.

# 5. Nem-típus sablonparaméterek (Non-Type Template Parameters)

Eddig a sablonjaink kacsacsőrei közé `< >` kizárólag típusokat (mint `int`, `double`, vagy `std::string`) helyettesítettünk be a `typename` vagy `class` kulcsszavak segítségével. De a C++ sablonrendszere ennél egy lépéssel tovább megy: **lehetőséget ad arra is, hogy konkrét, fordítási időben ismert értékeket adjunk át a sablonnak!**

Ezeket hívjuk nem-típus sablonparamétereknek (Non-Type Template Parameters).

### Miért jó ez nekünk?

Képzeld el, hogy egy fix méretű adatszerkezetet, például egy tömböt (Array) vagy egy mátrixot akarsz írni. Hagyományosan, ha a méretet a programozó határozza meg, a dinamikus memóriát (a *heap*-et) kellene használnod a `new` és `delete` operátorokkal. Ennek azonban van egy pici teljesítménybeli költsége, és magában hordozza a memóriaszivárgás veszélyét is.

A nem-típus sablonparaméterekkel a tömb méretét már **fordítási időben** fixálhatjuk. Ezzel a memória a sokkal gyorsabb *stack*-en (veremben) foglalódik le, dinamikus allokáció nélkül!



Lássuk, hogyan néz ki egy ilyen, típusbiztos és fix méretű `FixedArray` (FixTömb) osztály:

```cpp
#include <iostream>

// The template takes TWO parameters:
// 1. A Type (T) for the elements.
// 2. A Non-Type parameter (int Size) for the exact capacity.
template <typename T, int Size>
class FixedArray {
private:
    // We can use 'Size' directly to declare a static stack-array!
    T data[Size];

public:
    FixedArray() {
        // Initialize the array with default values
        for (int i = 0; i < Size; ++i) {
            data[i] = T(); 
        }
    }

    int getSize() const {
        return Size; // We can return the template parameter like a normal variable
    }

    void set(int index, T value) {
        if (index >= 0 && index < Size) {
            data[index] = value;
        } else {
            std::cout << "Error: Index out of bounds!" << std::endl;
        }
    }

    T get(int index) const {
        if (index >= 0 && index < Size) {
            return data[index];
        }
        std::cout << "Error: Index out of bounds!" << std::endl;
        return T(); 
    }
};

int main() {
    std::cout << "--- Non-Type Template Parameters ---" << std::endl;

    // We instantiate the class with the type 'int' AND the value '5'
    // The compiler generates a specific class where 'Size' is hardcoded to 5.
    FixedArray<int, 5> scores;
    
    scores.set(0, 100);
    scores.set(1, 95);
    
    std::cout << "Array size: " << scores.getSize() << std::endl;
    std::cout << "First score: " << scores.get(0) << std::endl;

    // We instantiate ANOTHER completely separate class for 'double' and '3'
    FixedArray<double, 3> coordinates;
    coordinates.set(0, 47.4979); // Latitude
    coordinates.set(1, 19.0402); // Longitude

    std::cout << "Coordinate array size: " << coordinates.getSize() << std::endl;

    return 0;
}
```

A fenti technika olyannyira hatékony és népszerű a C++-ban, hogy a standard könyvtár (STL) is pontosan így valósítja meg a modern, biztonságos tömbjét, a `std::array`-t (pl. `std::array<int, 5>`).

### A legfontosabb korlátozás: Fordítási idejű állandók

Mivel a C++ fordító a kód gépi kódra fordítása közben hozza létre ezeket az osztályokat, a sablonnak átadott értéknek **már a fordítás pillanatában ismertnek kell lennie**.

Ezt a kódot a fordító azonnal visszadobja hibával:

```cpp
int userSize;
std::cin >> userSize;

// HIBA! A 'userSize' értéke csak a program futása közben dől el,
// a fordító nem tud belőle osztályt generálni!
FixedArray<int, userSize> myArray; 
```

A nem-típus paraméterek helyére tehát csak konkrét számokat (`5`, `100`), vagy olyan konstansokat (`const int`, `constexpr`) írhatunk, amiknek az értéke előre, statikusan kódolva van.

# 6. Sablonspecializáció (Template Specialization)

A sablonok zseniálisak, mert adnak nekünk egy általános "receptet", ami a legtöbb típusra tökéletesen működik. De mi történik akkor, ha jön egy különleges típus (egy kivétel), amire az általános recept csődöt mond, vagy egyszerűen csak teljesen más, egyedi viselkedést szeretnénk neki adni?

Gondolj egy sütireceptre: az általános szabály az, hogy a tésztát be kell tenni a sütőbe 180°C-ra. De ha az a bizonyos "tészta" történetesen fagylalt, akkor az általános sablon katasztrófához vezet!

Ilyenkor használjuk a **sablonspecializációt** (Template Specialization). Ezzel azt mondjuk a fordítónak: *"Használd az általános sablont mindenre, KIVÉVE erre az egy konkrét típusra. Ha ezt a típust látod, használd ezt a teljesen egyedi megvalósítást!"*

### 1. Függvénysablonok specializációja

Vegyünk egy klasszikus példát: írunk egy generikus `isEqual` (egyenlő-e) függvényt, ami két értéket hasonlít össze a `==` operátorral. Ez tökéletesen működik számokra (`int`, `double`), de elbukik a klasszikus C-stílusú szövegeken (`const char*`), mert ott a `==` csak a memóriacímeket hasonlítaná össze, nem magát a szöveget!

Írjuk meg az általános sablont, és mellé a speciális kivételt a `const char*` típusra:

```cpp
#include <iostream>
#include <cstring> // Szükséges a strcmp függvényhez

// 1. Az ÁLTALÁNOS sablon (Minden típusra ez fut le alapértelmezetten)
template <typename T>
bool isEqual(T a, T b) {
    std::cout << "[Általános sablon hívva] ";
    return a == b;
}

// 2. A TELJES SPECIALIZÁCIÓ a 'const char*' típusra
// A 'template <>' jelzi a fordítónak, hogy ez egy specializált verzió, 
// és nem vezetünk be új 'T' paramétert.
template <>
bool isEqual<const char*>(const char* a, const char* b) {
    std::cout << "[Speciális sablon hívva const char*-ra] ";
    // Szövegek tartalmának összehasonlítása a C-s strcmp függvénnyel
    return std::strcmp(a, b) == 0; 
}

int main() {
    std::cout << "--- Template Specialization (Functions) ---" << std::endl;

    // Az int típus az általános sablont használja
    bool intResult = isEqual(10, 10);
    std::cout << "Eredmény: " << (intResult ? "Egyenlő" : "Nem egyenlő") << "\n\n";

    // A lefordított kód itt felismeri a const char* típust, és a specializált verziót hívja!
    const char* s1 = "Hello";
    const char* s2 = "Hello";
    bool stringResult = isEqual(s1, s2);
    std::cout << "Eredmény: " << (stringResult ? "Egyenlő" : "Nem egyenlő") << std::endl;

    return 0;
}
```

### 2. Osztálysablonok specializációja

Ugyanez a logika alkalmazható teljes osztályokra is. Tegyük fel, hogy írunk egy adatmegjelenítő `Formatter` osztályt. Az általános sablon egyszerűen kiírja az értéket a konzolra. Azonban a logikai értékeknél (`bool`) nem azt akarjuk látni, hogy `1` vagy `0`, hanem azt, hogy `IGEN` vagy `NEM`.

Készítsünk egy teljesen egyedi osztályt a `bool` típus számára!

```cpp
#include <iostream>

// 1. Az ÁLTALÁNOS osztálysablon
template <typename T>
class Formatter {
public:
    void print(T value) const {
        std::cout << "Általános érték: " << value << std::endl;
    }
};

// 2. A TELJES SPECIALIZÁCIÓ a 'bool' típusra
// Fontos: Az osztály neve után <bool> formában jelezzük a lekötött típust!
template <>
class Formatter<bool> {
public:
    // Itt a metódus már egy konkrét 'bool' paramétert vár, nem 'T'-t
    void print(bool value) const {
        std::cout << "Logikai érték: " << (value ? "IGEN" : "NEM") << std::endl;
    }
    
    // Akár teljesen új, egyedi metódusokat is tehetünk a specializált osztályba,
    // amik az általános sablonban nincsenek is benne!
    void printInverted(bool value) const {
        std::cout << "Invertált érték: " << (!value ? "IGEN" : "NEM") << std::endl;
    }
};

int main() {
    std::cout << "--- Template Specialization (Classes) ---" << std::endl;

    // Példányosítjuk az általános sablont egy 'double' típusra
    Formatter<double> doubleFormatter;
    doubleFormatter.print(3.1415); // Általános érték: 3.1415

    // Példányosítjuk a sablont 'bool' típusra - a fordító behelyettesíti a specializált osztályt!
    Formatter<bool> boolFormatter;
    boolFormatter.print(true);       // Logikai érték: IGEN
    boolFormatter.printInverted(true); // Invertált érték: NEM

    return 0;
}
```

### Miért olyan erős eszköz ez?

A sablonspecializáció adja meg a C++ fejlesztőknek azt a szabadságot, hogy a háttérben extrém mértékben optimalizálják a kódjukat. 
Például a C++ Standard Library (STL) `std::vector` tárolója (amit bár mi most nem használunk, de érdemes tudni róla) egy általános osztálysablon. Azonban létezik egy `std::vector<bool>` nevű **beépített specializációja**, ami a háttérben nem egy egész bájtot (8 bitet) pazarol el minden logikai értékre, hanem bitenként csomagolja össze őket, drasztikusan csökkentve a memóriahasználatot! A programozó ebből semmit nem vesz észre (neki csak egy sima vektornak tűnik), de a specializáció miatt a háttérben egy teljesen egyedi kód fut le.

# 7\. Fordítási modell és a "Header-Only" szabály

Ha valaha is próbáltál már osztálysablont írni, és a szokásos módon szétbontottad egy `.h` (deklaráció) és egy `.cpp` (implementáció) fájlra, szinte biztosan találkoztál már a C++ fejlesztők rémálmával: a linker hibával (pl. `unresolved external symbol` vagy `undefined reference`).

Ez a fejezet pontosan arról szól, miért történik ez, és hogyan kell helyesen kezelni a sablonokat a projektjeidben.

### Miért omlik össze a hagyományos `.h` és `.cpp` szétbontás?

A C++ fordító egy nagyon specifikus szabályrendszer szerint dolgozik: a `.cpp` fájlokat **egymástól teljesen függetlenül** fordítja le úgynevezett fordítási egységekké (Translation Units), majd a legvégén a Linker (szerkesztő) próbálja meg összekötni őket.

Képzeld el a következő szituációt:

1.  Van egy `Box.h` fájlod a sablon deklarációjával.
2.  Van egy `Box.cpp` fájlod a sablon metódusainak megvalósításával.
3.  A `main.cpp`-ben beinkludálod a `Box.h`-t, és létrehozol egy `Box<int>` objektumot.

Amikor a fordító a `main.cpp`-t olvassa, látja, hogy szüksége lenne egy `Box<int>` osztályra. Látja a deklarációt a headerben, de az implementáció nincs ott. A fordító arra gondol: *"Sebaj, biztos meglesz majd egy másik fájlban, a Linker majd összeköti\!"*

Amikor a fordító a `Box.cpp`-t olvassa, látja benne a sablon receptjét, de **mivel függetlenül fordul a `main.cpp`-től, fogalma sincs arról, hogy valaki valahol egy `int` típusú verziót kért belőle\!** Ezért nem generál le semmit a háttérben.

A végén a Linker megpróbálja összekötni a `main.cpp` igényét a `Box.cpp` tartalmával, de a `Box<int>` lefordított kódja sehol sem létezik. Bumm, a program elszáll egy kilométer hosszú linker hibával.

### A megoldás: A "Header-Only" (Csak fejléc) szabály

Mivel a fordítónak **ugyanabban a pillanatban (ugyanabban a fájlban)** kell látnia a sablon deklarációját és implementációját ahhoz, hogy a példányosítást (a kódgenerálást) el tudja végezni, a megoldás roppant egyszerű:

**A sablonok esetében az implementációt is a header (`.h` vagy `.hpp`) fájlba kell tenni\!**

Ez a "Header-Only" megközelítés. A C++ Standard Library (STL) sablonjai (mint a `std::vector` vagy `std::string`) is pontosan így vannak megírva: az egész kód a header fájlokban lakik.

Nézzük meg, hogyan néz ki egy helyes, modern Header-Only sablon fájl (pl. `Box.hpp` – a `.hpp` kiterjesztés gyakori a C++ sablonkönyvtáraknál, hogy jelezze: ez nem egy sima C header):

```cpp
#ifndef BOX_HPP
#define BOX_HPP

#include <iostream>

// 1. A sablon deklarációja
template <typename T>
class Box {
private:
    T item;

public:
    Box(T initialItem);
    T getItem() const;
};

// 2. A metódusok implementációja UGYANABBAN a fájlban!
// Közvetlenül az osztály definíciója alatt (vagy magában az osztályban inline).

template <typename T>
Box<T>::Box(T initialItem) : item(initialItem) {}

template <typename T>
T Box<T>::getItem() const {
    return item;
}

#endif // BOX_HPP
```

Ezután a `main.cpp`-ben egyszerűen csak `#include "Box.hpp"`, és a fordító minden információval rendelkezni fog, hogy azonnal legenerálja a kért \`Box\<int\>` vagy `Box<std::string>` osztályokat, anélkül hogy a linker panaszkodna.

### Van más megoldás? (Explicit példányosítás)

Létezik egy másik trükk is, ha mindenképp ragaszkodsz a `.cpp` fájlhoz: a `.cpp` fájl legvégén **explicit módon kikényszeríted** a fordítóból, hogy generálja le a specifikus típusokat.

*Példa a `Box.cpp` végén:*
```cpp
// ... a metódusok implementációja felette ...

// Kényszerítjük a fordítót, hogy generálja le ezeket a konkrét osztályokat:
template class Box<int>;
template class Box<double>;
template class Box<std::string>;
```

Ez működik, és a linker hiba eltűnik, de **nagyon rugalmatlan**, hiszen a `Box.cpp` írójának előre tudnia kell, hogy a jövőben a felhasználók milyen típusokkal akarják majd használni a sablont. Ezért a modern C++ fejlesztésben a sablonoknál a **Header-Only** megközelítés az iparági standard.
