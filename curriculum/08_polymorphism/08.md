# Polimorfizmus

## 1. Bevezetés a polimorfizmusba

Mi is az a polimorfizmus? Maga a szó görög eredetű, a *poly* (sok) és a *morph* (alak) szavakból tevődik össze, jelentése tehát **többalakúság**. Az objektumorientált programozásban (OOP) – így a C++-ban is – a tokozás (encapsulation) és az öröklődés (inheritance) mellett a harmadik legfontosabb alapelv.

A programozás nyelvére lefordítva ez azt jelenti, hogy **ugyanaz a művelet, hívás vagy interfész többféleképpen is viselkedhet attól függően, hogy pontosan milyen objektumon hajtjuk végre.**

### Valós életbeli analógia a megértéshez

Képzelj el egy állatidomárt, aki előtt három különböző állat ül: egy kutya, egy macska és egy kacsa. Az idomár kiad egyetlen, egységes utasítást: **„Hangot ad!”**

* A kutya erre ugatni fog: *„Vau-vau!”*
* A macska nyávogni kezd: *„Miau!”*
* A kacsa pedig hápog: *„Háp-háp!”*

Az idomárnak (vagyis a programunk azt használó részének) nem kellett három különböző, specifikus utasítást megtanulnia (mint például `kutyaugatas()`, `macskanyavogas()`, `kacsahapogas()`). Elég volt egyetlen, általános parancsot (`hangot_ad()`) ismernie és kiadnia. A polimorfizmus varázsa éppen abban rejlik, hogy az adott állat (az objektum) a **saját belső típusának megfelelően** reagál erre az általános utasításra.

### A polimorfizmus előnyei a gyakorlatban

Miért éri meg ezt a koncepciót használni a kódolás során?

* **Rendkívüli rugalmasság:** Lehetővé teszi, hogy különböző típusú (de közös őssel rendelkező) objektumokat egységesen kezeljünk. Például egy játékban egyetlen tömbben tárolhatod az összes ellenséget (Ork, Goblin, Sárkány), és egyetlen egyszerű ciklussal meghívhatod mindegyikre a `tamadas()` függvényt.
* **Kiváló bővíthetőség:** Ezt hívják a programozásban *Open/Closed Principle*-nek (Nyitott/Zárt elv). Ha a jövőben behozol egy új állatot (pl. egy tehenet) vagy egy új ellenséget a kódba, a meglévő vezérlő logikát **egyáltalán nem kell módosítanod**. Az új osztály egyszerűen becsatlakozik a rendszerbe, és tudni fogja a dolgát. A rendszer nyitott a bővítésre, de zárt a meglévő kód módosítására.
* **Kevesebb és tisztább kód:** Nem kell hosszú, átláthatatlan `if-else` vagy `switch` szerkezeteket írnod a kódba csak azért, hogy ellenőrizd, épp milyen típusú objektummal van dolgod. A C++ a háttérben automatikusan eldönti, hogy melyik osztály specifikus függvényét kell meghívni.

## 2. A polimorfizmus típusai C++-ban

Alapvetően két nagy csoportra bontjuk a polimorfizmust aszerint, hogy **mikor dől el**, pontosan melyik kód fog lefutni: fordítási időben (statikus) vagy futási időben (dinamikus).


### Statikus (fordítási idejű) polimorfizmus

Itt a fordítóprogram (compiler) már akkor pontosan tudja, hogy melyik függvényt vagy metódust kell meghívnia, amikor a kódot gépi kódra fordítja. Ezt a folyamatot hívják **korai kötésnek (early binding)**. Mivel minden döntés előre megszületik, ez a típus rendkívül gyors, a program futása közben nincs extra teljesítménybeli költsége (overhead).

Három fő megvalósítási módja van C++-ban:

1.  **Függvény-túlterhelés (Function Overloading):**
    Ugyanazzal a névvel hozhatsz létre több függvényt a kódodon belül, feltéve, hogy a paramétereik listája (a paraméterek típusa vagy száma) eltér.
    ```cpp
    void print(int number) { cout << "Egész szám: " << number << endl; }
    void print(double number) { cout << "Tört szám: " << number << endl; }
    void print(string text) { cout << "Szöveg: " << text << endl; }
    // A fordító a paraméter alapján egyértelműen eldönti, melyiket kell meghívni.
    ```

2.  **Operátor-túlterhelés (Operator Overloading):**
    A beépített operátorok (mint a `+`, `-`, `==`) viselkedését saját hatáskörben átdefiniálhatod a saját osztályaidra. Így például összeadhatsz két `Matrix` vagy `Pont` objektumot a hagyományos `+` jellel, mintha csak sima számok lennének.

3.  **Sablonok (Templates / Generikus programozás):**
    Olyan kódot írhatsz, amely a típusoktól függetlenül, általánosan működik. A fordító a fordítás pillanatában generálja le a megfelelő, típusfüggő kódot a megadott típus alapján.

### Dinamikus (futási idejű) polimorfizmus

Ez a klasszikus, objektumorientált polimorfizmus (és ez a tananyagunk fő fókuszpontja). Ilyenkor a fordító a fordítás pillanatában még *nem tudja* biztosan, hogy melyik függvény fog lefutni. A döntés csak a program **futása közben** születik meg, az objektum tényleges, memóriában lévő típusa alapján. Ezt hívják **késői kötésnek (late binding)** vagy dinamikus kötésnek (dynamic binding).

Ehhez a következőkre van szükség:
* **Öröklődés (Inheritance):** Kell egy közös ősosztály és legalább egy abból származtatott osztály.
* **Alaposztálybeli mutató vagy referencia:** Mutatókon (`*`) vagy referenciákon (`&`) keresztül kell hivatkoznunk a származtatott objektumokra.
* **Virtuális függvények (`virtual`):** Az ősosztályban egy speciális kulcsszóval kell jelezni, hogy az adott metódus felüldefiniálható, és futásidőben kell feloldani.

## 3. A dinamikus polimorfizmus alapjai

A dinamikus polimorfizmus megvalósításához C++-ban három dolog együttes jelenléte szükséges: öröklődés (Inheritance), alaposztálybeli mutatók/referenciák (Upcasting), és a `virtual` kulcsszó. Nézzük meg ezeket lépésről lépésre!

### Upcasting: Alaposztály mutatók és referenciák

Az **Upcasting** (felfelé kasztolás) azt a folyamatot jelenti, amikor egy származtatott (gyerek) osztálybeli objektumra az ősosztály (szülő) mutatójával (`pointer`) vagy referenciájával hivatkozunk. 

Mivel egy `Dog` objektum memóriaképe magában foglalja a teljes `Animal` részt is (hiszen a kutya *egy* állat, ez az ún. *is-a* kapcsolat), a C++ megengedi ezt a konverziót, ráadásul teljesen automatikusan és biztonságosan.

Ha azonban csak simán létrehozunk egy mutatót, és meghívunk rajta egy metódust, a fordító a **mutató típusa** (azaz az `Animal`) alapján fogja meghívni a függvényt, nem pedig az alapján, hogy ténylegesen mi van a memóriában (a `Dog`). Itt jön képbe a varázsszó.

### A `virtual` kulcsszó szerepe

Ahhoz, hogy a fordító tudja, hogy a döntést a futási időre kell halasztania (késői kötés), a metódust az ősosztályban `virtual` (virtuális) kulcsszóval kell ellátnunk.

Amikor a C++ meglátja a `virtual` szót, azt mondja: *"Rendben, amikor ezt a függvényt egy mutatón vagy referencián keresztül hívják meg, nem dőlök be a mutató típusának. Futásidőben megnézem a memóriát, és az objektum tényleges, valós típusához tartozó függvényt hívom meg!"*

### Modern C++: Az `override` és a `final`

A C++11 két nagyon hasznos kulcsszót vezetett be, hogy biztonságosabbá tegye a polimorf kódot:

* **`override`**: A származtatott osztályban a függvény deklarációjának végére írjuk. Ezzel explicit módon jelezzük a fordítónak a szándékunkat: *"Ezzel a függvénnyel felül akarok írni egy virtuális ős-függvényt"*. Ha véletlenül elírjuk a metódus nevét, vagy más paramétereket adunk meg, a kód nem fog lefordulni. Megvéd minket a nehezen detektálható bugoktól!
* **`final`**: Ha ezt írjuk egy virtuális függvény végére, azzal megtiltjuk, hogy az öröklődési láncban lejjebb lévő osztályok tovább felülírják azt. (Osztály neve után írva pedig a további öröklődést tiltja le).

### Kódpélda: A polimorfizmus működés közben

Nézzük meg hogyan áll össze ez a három koncepció:

```cpp
#include <iostream>
#include <vector>

// Base class
class Animal {
public:
    // The 'virtual' keyword enables dynamic polymorphism (late binding)
    virtual void speak() const {
        std::cout << "Animal makes a generic sound." << std::endl;
    }

    // A virtual destructor is critical for polymorphic base classes! 
    // (We will dive deep into this in Chapter 6)
    virtual ~Animal() = default; 
};

// Derived class 1
class Dog : public Animal {
public:
    // 'override' ensures we strictly match the base class signature
    void speak() const override {
        std::cout << "Dog barks: Woof! Woof!" << std::endl;
    }
};

// Derived class 2
class Cat : public Animal {
public:
    void speak() const override {
        std::cout << "Cat meows: Meow!" << std::endl;
    }
};

// A function demonstrating Upcasting via reference
void makeAnimalSpeak(const Animal& animal) {
    // The correct speak() is called based on the ACTUAL object passed in
    animal.speak(); 
}

int main() {
    Dog myDog;
    Cat myCat;

    std::cout << "--- Passing by Reference ---" << std::endl;
    makeAnimalSpeak(myDog); // Output: Dog barks: Woof! Woof!
    makeAnimalSpeak(myCat); // Output: Cat meows: Meow!

    std::cout << "\n--- Upcasting via Pointers ---" << std::endl;
    // Base class pointers pointing to derived objects
    Animal* animalPtr1 = new Dog();
    Animal* animalPtr2 = new Cat();

    // The magic of late binding:
    animalPtr1->speak(); // Output: Dog barks: Woof! Woof!
    animalPtr2->speak(); // Output: Cat meows: Meow!

    // Cleanup
    delete animalPtr1;
    delete animalPtr2;

    return 0;
}
```

## 4. Absztrakt osztályok és interfészek

Az előző példában létrehoztunk egy általános `Animal` osztályt, aminek volt egy saját `speak()` metódusa. Gondoljunk bele: van értelme a valóságban példányosítani (létrehozni) egy "általános állatot"? Milyen hangot ad ki egy általános állat? A valóságban kutyák, macskák, madarak vannak. 

Gyakran előfordul, hogy egy ősosztályt **kizárólag arra szeretnénk használni, hogy egy közös alapot (szerződést) biztosítson** a leszármazottaknak, de önmagában nem akarjuk, hogy bárki is létrehozzon belőle egy objektumot. Erre valók a tisztán virtuális függvények és az absztrakt osztályok.

### Tisztán virtuális függvények (Pure Virtual Functions)

Ha egy virtuális függvénynek nem adunk meg törzset az ősosztályban, hanem egyenlővé tesszük nullával (`= 0`), akkor azt **tisztán virtuális függvénynek** nevezzük.

Ezzel a szintaxissal egy nagyon erős üzenetet küldünk a fordítónak és a többi programozónak: *"Ennek a függvénynek itt nincs alapértelmezett viselkedése. Bármelyik osztály, ami ebből az ősosztályból származik, KÖTELEZŐ, hogy megírja a saját verzióját erre a függvényre."*

### Mi az az absztrakt osztály?

A C++-ban a szabály végtelenül egyszerű: **Bármely osztály, amely tartalmaz legalább egy tisztán virtuális függvényt, absztrakt osztállyá válik.**

Az absztrakt osztályoknak van egy nagyon fontos tulajdonsága: **Nem lehet belőlük példányt (objektumot) létrehozni!** Ha megpróbálod, a fordító azonnal hibát dob. Mutatót (pointert) vagy referenciát viszont továbbra is készíthetünk belőlük, hiszen pontosan ez kell a polimorfizmushoz.

### Interfészek (Interfaces) C++-ban

Szemben a Javával vagy a C#-pal, a C++ nyelvben nincs külön `interface` kulcsszó. Ennek ellenére a koncepció tökéletesen megvalósítható.

C++-ban egy **interfész** egy olyan absztrakt osztály, amely:
1. Kizárólag tisztán virtuális függvényeket tartalmaz (nincs benne implementált metódus).
2. Nincsenek adattagjai (változói).
3. Van egy virtuális destruktora (erről a 5. részben beszélünk részletesen, de az interfészeknél kötelező elem).

Az interfészek neveit a konvenciók szerint gyakran nagy 'I' betűvel kezdjük (pl. `IDrawable`, `ILogger`). Egy interfész egy "szerződés": aki megörökli, annak garantálnia kell, hogy megvalósítja az abban foglalt funkciókat.

### Kódpélda: Alakzatok és Interfészek

Nézzük meg egy klasszikus példán, hogyan épül fel egy interfész, és hogyan kényszeríti ki a megfelelő megvalósítást:

```cpp
#include <iostream>

// Interface: Contract for anything that can be drawn
// We use the 'I' prefix as a naming convention for Interfaces
class IDrawable {
public:
    // Pure virtual function: marked with '= 0'
    // This makes IDrawable an Abstract Class!
    virtual void draw() const = 0; 
    
    // Pure virtual function for calculating area
    virtual double getArea() const = 0;

    // Interfaces must always have a virtual destructor
    virtual ~IDrawable() = default; 
};

// Concrete class 1: Circle
// It MUST implement draw() and getArea() to be instantiable
class Circle : public IDrawable {
private:
    double radius;

public:
    Circle(double r) : radius(r) {}

    // Fulfilling the contract
    void draw() const override {
        std::cout << "Drawing a Circle with radius: " << radius << std::endl;
    }

    double getArea() const override {
        return 3.14159 * radius * radius;
    }
};

// Concrete class 2: Rectangle
class Rectangle : public IDrawable {
private:
    double width, height;

public:
    Rectangle(double w, double h) : width(w), height(h) {}

    // Fulfilling the contract
    void draw() const override {
        std::cout << "Drawing a Rectangle (" << width << "x" << height << ")" << std::endl;
    }

    double getArea() const override {
        return width * height;
    }
};

int main() {
    // IDrawable shape; // ERROR: Cannot instantiate abstract class!

    // We can use interface pointers!
    IDrawable* shape1 = new Circle(5.0);
    IDrawable* shape2 = new Rectangle(4.0, 6.0);

    // Polymorphism in action
    shape1->draw();
    std::cout << "Area: " << shape1->getArea() << std::endl;

    shape2->draw();
    std::cout << "Area: " << shape2->getArea() << std::endl;

    delete shape1;
    delete shape2;

    return 0;
}
```

Ebben a példában az `IDrawable` egy tökéletes interfész. Garantálja, hogy bármi, ami ebből származik, rajzolható lesz, és lesz területe, miközben maga az interfész nem tartalmaz semmilyen implementációs részletet.

## 5. Polimorfizmus és memóriakezelés

Amikor dinamikus polimorfizmust használunk, szinte mindig a dinamikus memóriában (a *heap*-en) hozzuk létre az objektumainkat a `new` operátorral, majd ezekre ősosztály típusú mutatókkal (pointerekkel) hivatkozunk. 

Mivel a C++-ban nincs beépített szemétszedő (Garbage Collector), mint a Javában vagy a C#-ban, a `new` kulcsszóval lefoglalt memóriát nekünk kell manuálisan felszabadítanunk a `delete` operátorral. És pontosan itt leselkedik ránk a polimorfizmus egyik legnagyobb csapdája!

### A virtuális destruktorok fontossága (Kritikus szabály!)

Képzeld el a következő szituációt: dinamikusan létrehozol egy `Dog` objektumot, és a címét egy `Animal*` mutatóban tárolod. Amikor végeztél vele, kiadod a `delete` utasítást erre a mutatóra.

Ha az ősosztály (`Animal`) destruktora **nem** virtuális, akkor a C++ a fordítási időben ismert mutató típusa alapján fog cselekedni (korai kötés). Vagyis **csak az `Animal` destruktorát fogja meghívni**, a `Dog` osztály saját destruktora sosem fut le! 

Miért baj ez? Ha a származtatott osztályod (pl. a `Dog`) a saját konstruktorában memóriát foglalt (mondjuk egy tömbnek), akkor az a memória sosem fog felszabadulni, mert a destruktora nem futott le. Ezt hívjuk **memóriaszivárgásnak (memory leak)**, ami idővel a program összeomlásához vezethet.

**A C++ polimorfizmusának aranyszabálya:** Ha egy osztálynak van *bármilyen* virtuális függvénye, vagy ha egyáltalán arra tervezed, hogy alaposztályként használják, akkor a destruktorát **kötelező** `virtual` kulcsszóval ellátni!

### Kódpélda: Biztonságos memóriakezelés nyers mutatókkal

Nézzük meg egy klasszikus példán, hogyan kell helyesen használni a `new` és `delete` operátorokat polimorfikus környezetben, hogy elkerüljük a memóriaszivárgást:

```cpp
#include <iostream>

// Base class
class Weapon {
public:
    Weapon() { 
        std::cout << "Weapon created." << std::endl; 
    }
    
    // CRITICAL: Virtual destructor!
    // This guarantees that derived destructors will be called when we delete
    // a base class pointer.
    virtual ~Weapon() { 
        std::cout << "Weapon destroyed." << std::endl; 
    }

    virtual void attack() const = 0; // Pure virtual function
};

// Derived class
class Sword : public Weapon {
private:
    int* damageEnhancers; // Dynamically allocated array for demonstration

public:
    Sword() {
        std::cout << "Sword created." << std::endl;
        // Allocating memory inside the derived class
        damageEnhancers = new int[5]; 
    }

    // If Weapon::~Weapon() wasn't virtual, this ~Sword() would NEVER run, 
    // causing a memory leak of the damageEnhancers array!
    ~Sword() override {
        std::cout << "Sword destroyed. Cleaning up array." << std::endl;
        delete[] damageEnhancers; // Freeing the derived class memory
    }

    void attack() const override {
        std::cout << "Swinging the sword! Slash!" << std::endl;
    }
};

class Bow : public Weapon {
public:
    Bow() { std::cout << "Bow created." << std::endl; }
    ~Bow() override { std::cout << "Bow destroyed." << std::endl; }

    void attack() const override {
        std::cout << "Shooting an arrow! Swoosh!" << std::endl;
    }
};

int main() {
    std::cout << "--- Entering battle phase ---" << std::endl;
    
    // Polymorphism using raw pointers and dynamic allocation
    Weapon* weapon1 = new Sword();
    Weapon* weapon2 = new Bow();

    std::cout << "\nAttacking enemies:\n";
    weapon1->attack();
    weapon2->attack();

    std::cout << "\nCleaning up memory:\n";
    // Because Weapon has a virtual destructor, 'delete weapon1' will first
    // call ~Sword() to clean up the array, and then ~Weapon().
    delete weapon1; 
    delete weapon2;

    std::cout << "--- Battle phase ended ---" << std::endl;

    return 0;
}
```
